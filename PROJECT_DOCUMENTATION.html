Plain-language overview

This project is a web application for examining the geometric complexity of radiotherapy treatment plans. A user uploads one or more RT Plan DICOM (.dcm) files and receives an Excel workbook of measurements for the treatment beams found in those plans.

In a modern radiotherapy machine, narrow metal leaves—called a multi-leaf collimator (MLC)—move while radiation is delivered. Together, the leaves form an opening, or aperture, that shapes the radiation beam. Openings that are small, irregular, off-centre, or changing rapidly can be more complex to deliver. This application turns that shape and motion information into numerical metrics that can be reviewed, compared, or used in a wider quality-assurance workflow.

The application makes the calculations repeatable and convenient: rather than manually extracting leaf positions and monitor units from every plan, a user can upload a batch of plans and download one spreadsheet.

Important clinical boundary. These measurements describe plan geometry and programmed delivery weights only. They do not calculate dose, verify delivery, assess patient safety, or decide whether a plan is clinically acceptable. Qualified clinical staff should interpret them alongside established validation and quality-assurance processes.

Who it is for and key terms

The application is intended for medical physicists, dosimetrists, researchers, and quality-assurance teams. Its usual workflow requires no programming: upload files, review the table, and download Excel. Developers can also reuse the calculation module from Python.

What happens when a plan is uploaded

  1. The user chooses one or more RT Plan DICOM files in the browser.
  2. The Streamlit interface reads each file in memory; it does not deliberately save the upload to a project folder.
  3. pydicom reads the DICOM content.
  4. The extraction code finds eligible dynamic, MLC-equipped beams and gathers leaf boundaries, leaf positions, delivery weights, and planned MU.
  5. The calculation code derives aperture areas and complexity metrics for each eligible beam.
  6. The processing bridge forms and combines spreadsheet rows, previews the first 200, and creates aperture_metrics_summary.xlsx with a Summary sheet.

Information included and excluded

For each eligible beam, the software uses the planned beam MU from the first fraction group, MLC leaf-pair boundaries, MLC positions at every control point, and cumulative meterset weights. When a control point does not repeat an unchanged MLC position, the most recently stated position is carried forward.

A beam is included only if it has an MLCX or MLCY device, more than two control points, and a matching planned BeamMeterset in the first fraction group. The web interface includes all eligible beams; direct Python use can filter on selected beam names.

The current calculation does not use RT Structure Set, dose, imaging, patient anatomy, delivery logs, or jaw positions. It collects gantry angle but does not use it in a formula. It does not estimate clinical dose or outcome.

How the calculation works

For every control point, the program finds each leaf-pair opening:

leaf gap = right-bank position − left-bank position

A negative opening becomes zero. Each open gap is multiplied by that leaf pair’s width; the sum is the aperture area. A segment uses the average of the two surrounding control-point areas. Segment values are weighted by delivered MU, so portions that deliver more planned radiation have greater influence.

Metrics use the same foundation but highlight different characteristics. Compare values only where plan types, machines, workflow, and configuration are consistent.

Mean dose-rate variation uses the mean available control-point dose rate as its reference and gantry travel in degrees as arc length. If dose rates are absent or all zero, the exported value is blank. PI and plan MLT are calculated across eligible MLC beams only. The calculation also returns mean AAV and LSV and intermediate dynamic entropy and dynamic aperture-change values, which are not exported.

Edge metric settings

M = sum over segments of [Wi × (C1 × xi + C2 × yi) / Ai] / total MU
P = C × M

Wi is segment MU, Ai is segment area, xi is exposed leaf-end length, and yi is exposed leaf-side length. C1 and C2 weight ends and sides; C scales M to P. All default to 1.0. Use other settings only for a documented local reason, because results with different settings are not directly comparable.

Dynamic Aperture Entropy

For each control-point pair, the app measures average absolute leaf-gap change and divides it by the largest leaf opening in the beam. It places these changes in five equally sized bins, calculates a normalised Shannon entropy, and multiplies it by the MU-weighted mean normalised change. In plain terms, ADE reflects both how much apertures change and how varied the changes are.

Using the web application

First-time setup (Windows PowerShell)

python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

If PowerShell blocks activation for this session, the project includes the optional command below. It affects only the current PowerShell process; follow organisational security guidance.

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force

Start and process

streamlit run streamlit_app.py
  1. Leave C1, C2, and C at 1.0 unless local requirements say otherwise.
  2. Upload one or more RT Plan DICOM files.
  3. Wait for the progress indicator; failed files show a warning.
  4. Review the preview table, then select Download Excel summary.

The preview displays at most 200 rows; the downloaded workbook contains the full summary. It has one row per eligible beam, not necessarily one row per file. The current export does not include source filename or beam name, so preserve that relationship elsewhere when traceability matters.

Data handling and privacy

The browser workflow processes uploads in memory during the current app session. It reads DICOM PatientID and writes it to the spreadsheet’s Plan ID column. RT Plan files and identifiers may be sensitive health information. Use approved systems, access controls, storage, and sharing procedures; in-memory processing does not remove privacy, security, or retention obligations.

Known limitations and practical checks

  • The program expects conventional RT Plan data with fraction group, beam, limiting-device, and control-point information. Missing or unusual data may trigger an error or warning.
  • Only the first fraction group is used for planned beam MU.
  • The first control point must provide usable MLC positions; later omitted positions are carried forward.
  • Beams without MLC, with two or fewer control points, or without matching planned MU are left out without a separate exclusion report.
  • If both MLCX and MLCY exist, the code chooses MLCX; it does not combine them.
  • No automated comparison with delivery logs or independent reference calculation is performed.
  • Zero-area cases can yield NaN; review them before later analysis.
  • The app is intended for relatively small batches. Larger uploads or high concurrent use may require different deployment and storage design.

Before operational use, test representative plans—including expected exclusions and edge cases—against independently reviewed reference results.

Reference

The project uses a specific selection and interpretation of metrics; consult that paper and locally approved methodology for research or clinical quality-assurance use.
